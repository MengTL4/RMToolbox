# 接入层按游戏家族收敛为引擎适配器，能力声明进接口

ADR 0001 把接入逻辑收敛成一份启动路线目录，但目录只回答"桥怎么送进去"，没有回答"送进去之后做什么、这个游戏支持什么"——这两件事目前散落在 launcher、attach、桥代码和 GUI 的硬编码分支里。我们决定：**按游戏家族把接入逻辑组织为引擎适配器**，一个适配器覆盖一个家族（`nwjs` 覆盖 MV/MZ，`rgss` 覆盖 XP/VX/VXAce，MKXP 作为 rgss 家族的变体），适配器拥有四件套接口——**detect**（向扫描器贡献指纹规则）、**plan**（产出启动/附加方案）、**payload**（在游戏脚本虚拟机里求值的桥代码）、**capabilities**（本家族支持的修改能力集合，GUI 据此按能力渲染）。桥协议只在宿主侧统一为桥会话抽象，游戏内传输各家族保持现状。这是借鉴 MTool 的"家族级适配 DLL + 统一回连"架构，但只取适配层，不取它的文本钩子实现（本工具以修改为主，不做翻译）。

## 为什么

- **家族级而不是版本级**：XP/VX/VXAce 共用 RGSS 解释器，MV/MZ 的 JS 侧几乎同构，版本差异（数据格式、少量类名、有无独立开关）适合在适配器内运行时探测处理。按版本拆五个适配器只会复制实现，违背"适配一类游戏"的目的。
- **capabilities 必须进接口**：现状是 GUI 隐式假设所有游戏都有同一组能力，但 XP 没有独立开关、各版本角色结构不同。能力声明让"这个游戏支持什么"成为数据，trainer locks 等功能也能按能力裁剪。
- **不统一游戏内协议**：MTool 让所有引擎收敛到一套回连协议，是为了"一个 DLL 二进制到处用"；我们的载荷本来就要 eval 进不同的 VM（JS vs Ruby），消息格式统一省不下什么，反而要让 Ruby 侧迁就 JS 的形状。GUI 和 trainer 需要的是宿主侧的统一会话接口，不是传输层的一刀切。

## 取舍

- **附着层通用化滞后于适配器层**：现有 8 条启动路线原样保留，先被适配器的 plan 包装；之后再补入口点注入（挂起创建 → OEP 注入 → 恢复），替换对 nb/enigma/grover 壳"裸启动盲等 30–60 秒再注入"的最脆一段。侧加载（winmm/version 代理 DLL）会往游戏目录写文件，违背"不改游戏文件"的路线哲学，只作为可选时机最后加。最终路线模型收敛为"附着时机 × 引擎适配器"的二维组合，路线目录不被推翻，而是被重新解释。
- **策略默认仍来自扫描器现场推导，不转向 MTool 的按游戏固化记录**：只持久化与默认不同的部分（策略覆盖记录），用户在路线下拉框手动选过后自动记住，并提供"恢复自动"入口。全量固化会让扫描器的改进对已入库游戏失效。

## 后果

- 新增一类游戏 = 新增一个适配器模块，不再触碰 launcher/attach/GUI 的公共路径。
- GUI 的修改器面板按 capabilities 数据驱动渲染；某家族不支持的能力不呈现，而不是点了报错。
- 扫描器的指纹规则迁往各适配器的 detect，扫描器本身退化为编排者。
- CONTEXT.md 新增「引擎适配器」「桥接载荷」「能力声明」「附着时机」「入口点注入」「策略覆盖记录」六个词。
