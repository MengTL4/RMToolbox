# 拒绝参数的壳不再兜底代启动：dll 启动路线退役，只留附加

`dll` 路线（userGoal「壳拒绝参数时的兜底」）曾经是 nb-evalnwbin / enigma-nb / grover-boot 三类壳的唯一启动路线：工具箱不带任何参数地把游戏裸启动起来（`cmd /c start` 一死一跑的父进程伎俩、两跳 PowerShell ShellExecute 链、以及后来的入口点注入），再等保护检查结束后投递 DLL 桥。我们决定：**整条 dll 启动路线退役——工具箱不再代这些游戏启动；用户自己双击启动游戏，再点「附加到运行中」**。标准 NW.js 游戏随之失去 dll 这个显式/回退候选（保留扩展启动与影子目录），入口点注入（OEP）机器一并删除。

## 为什么

- **裸启动兜底是整个接入面最脆的一段**。两种 spawn 机制都是和杀软/壳的祖先检查抢时间的启发式（实测被拦截时 60 秒双机制全灭），入口点注入则是为了补它的盲区又加的一层悬挂注入。可靠性修不到"可交付"，按钮却把它呈现成和其他路线同等的一键入口。
- **附加路径本来就完整存在**：`attachNw` 对运行中游戏的文件通道/WebSocket 投递、重试、权限诊断都已实测可用，不依赖任何启动伎俩。让壳游戏走"用户启动 → 附加"，每一步的失败原因都是可解释、可重试的。
- **计划层说实话比按钮层逞强好**：此前计划给壳游戏选出一条"名义上的启动路线"，按钮写着"启动并注入（裸启动，不加任何启动参数）"，失败时用户看到的是"被杀软拦截"。现在计划直接不产启动候选，卡片只留「附加到运行中」并把"手动启动后附加"写成提示。

## 取舍

- **删掉而不是留着不用**：`launchNw`、两种 spawn、`spawnNwGameAndWait`、OEP 三件（`oepLaunchEligible` / `launchOepInject` / `tryOepLaunch`）、启动专用的目录缓存预热（`ensureSealedCatalog`）和 bootstrap 的 bootTap/dance 变体全部删除——留着的"死代码"会被误读成仍在支持的能力。目录缓存由桥接在运行中捕获时自行落盘（08-capture.js）。
- **grover-boot 保留影子目录路线**：它有可补丁的 bg-script 时仍可由工具箱启动；没有时同样只能附加。
- **过期的策略覆盖记录自愈**：记住过 `dll` 的游戏在下次启动时因路线不再出现在候选中而被忽略并回收（既有机制，见 0002 的策略覆盖记录）。

## 后果

- `core/launch-routes.mjs` 不再有 `dll` 启动路线和 `nw-launch-inject*` / `nw-launch-oep` 策略字符串；DLL 附加只作为附加策略（`nw-inject` / `nw-inject-file`）的机制存在。
- 壳游戏的计划 `selected` 为 `null`、`error` 写明"请自行双击启动游戏，进入游戏后点「附加到运行中」"；GUI 据此隐藏「启动并注入」，把「附加到运行中」提为卡片主按钮。
- `GameRuntime` 不再有 `launchInject` 分发分支；`launcher.mjs` 的壳守卫报错改为指引手动启动 + 附加。
- CONTEXT.md 的「附着时机」去掉入口点注入；「启动并注入」收窄为不适用于拒绝参数的壳。
